Claude Code Skill TDD 强制 Delta Spec Archive 归档

📐 核心理念：四层金字塔 + Archive

文档冲突时，上层效力高于下层。所有活跃变更必须通过 Delta Spec 隔离，禁止直接修改锁定的真相源。

constitution.md — 最高约束
spec.md — 需求真相源
plan-{module}.md — 模块设计（锁定后只读）
source code — 设计的实现
archive/ — 历史归档（只读审计追踪）

📄 真相源单一

spec.md 和 plan-*.md 只反映当前已完成的系统状态。"计划中"的变更在 changes/ 中管理。

🔀 变更隔离

所有活跃变更通过 changes/proposal-{NNNN}.md 管理。ADDED / MODIFIED / REMOVED 显式标记，人类和 AI 无需 diff 即可理解。

📦 Archive 归档

完成的 proposal 和旧版 plan 归档到 archive/，保留完整设计谱系。不是删除，而是成为只读的审计历史。

🔄 三轨道工作流

v2.0 将六阶段压缩为三轨道，降低认知负担，同时保留核心纪律。

轨道一：初始化

/sdd-init
/
/sdd-adopt

新项目用 /sdd-init（Greenfield），已有项目用 /sdd-adopt（Brownfield）反推 spec。

轨道二：演进（核心）

/sdd-propose
→
/sdd-implement
→
/sdd-archive

借鉴 OpenSpec 的 Propose → Apply → Archive 三阶段。每个变更先创建 Delta Spec，实现后合并归档。

轨道三：验证

/sdd-verify

贯穿全程的一致性检查：文档存在性、追溯链、Plan-代码一致性、Delta Spec 合规性、测试覆盖。

⌨️ 命令速查

/sdd-init 初始化新项目目录结构，生成 constitution.md + spec.md 骨架（可选完整版/轻量版） [初始化]
/sdd-adopt 已有代码库引入 SDD：反推 spec/plan，标记基线，识别技术债 [初始化]
/sdd-propose 创建变更提案（Delta Spec）：判定 Type-A/B/C/D，输出 changes/proposal-{NNNN}.md [演进]
/sdd-implement 按 TDD 红-绿-重构实现提案：RED → GREEN → REFACTOR，状态改为 IMPLEMENTED [演进]
/sdd-archive 将 proposal 合并到真相源（spec/plan），归档旧版，触发 verify [演进]
/sdd-verify 一致性验证：文档存在性、追溯链、Plan-代码一致性、Delta 合规、测试覆盖 [验证]

🔀 Delta Spec 增量规格

v2.0 核心机制。所有变更必须通过 changes/proposal-{NNNN}.md 管理，禁止直接修改锁定的真相源。

变更类型判定

类型 判定依据 处理方式
Type-A 需求变更 spec 中的功能需求增删改 创建 proposal → 更新 spec delta → 更新 plan delta → 实现 → archive
Type-B 设计变更 plan 中接口/行为变更，spec 未变 创建 proposal → 更新 plan delta → 实现 → archive
Type-C 代码缺陷 实现与 plan 不符（纯代码错误） 无需 proposal，直接修复代码
Type-D 技术债重构 代码行为不变，内部结构优化 可选创建 proposal（推荐），或直接用测试保护重构

Proposal 文件格式

# Proposal 002: 数据质量校验

| 属性 | 内容 |
|------|------|
| 类型 | Type-A（需求变更）|
| 状态 | PROPOSED → APPROVED → IMPLEMENTED → ARCHIVED |

## 变更内容

[ADDED] spec: 新增 F4「数据质量校验」
[ADDED] plan-core: DC-0004 质量规则 DSL
[MODIFIED] plan-core: 超时默认值 30s → 60s
[REMOVED] plan-frontend: 废弃的一键诊断按钮逻辑

## 影响评估
| 层级 | 影响 | 说明 |
|------|------|------|
| spec.md | 是 | 新增 F4 |
| plan-core.md | 是 | 新增 DC-0004，修改 DC-0001 |
| plan-scheduler.md | 否 | 接口契约不变 |

## 实现检查清单
- [ ] 失败测试（RED）
- [ ] 最小实现（GREEN）
- [ ] 重构（REFACTOR）
- [ ] 回归测试通过
- [ ] Archive 合并

Archive 合并纪律

🚫 禁止逆序

不允许先改代码再补 proposal 合并（RED-5）。必须先 proposal，后实现，再 archive。

🚫 禁止范围外变更

一次 proposal 只解决一个问题。禁止「顺手改」未评估的代码。

✅ 强制回归

任何 archive 合并后，必须验证未变更模块的测试仍然通过。

📁 目录结构

│   ├── archive/                    # ⭐ 历史归档（只读审计追踪）
│   │   ├── proposal-{NNNN}-merged.md
│   │   └── plan-{module}-v{X}.{Y}.{Z}.md
│   ├── assets/                     # 文档图片、图表

│   ├── scripts/                    # 开发辅助脚本

DIR-1

Document/ 下绝不放置可执行代码

DIR-2

SourceCode/ 下绝不放置设计文档（README 除外）

DIR-3

changes/ 中仅存放活跃提案，IMPLEMENTED 后必须 archive

🚫 红色条款（绝对禁区）

编号 禁止行为 违规后果
RED-1 无 plan 直接编码。公共接口进入代码前必须有对应 plan 定义。 视为技术债，必须补 plan 或移除代码
RED-2 plan 与代码不一致。接口、行为与实现出现偏差。 视为缺陷，必须修复使之一致
RED-3 未经审阅的 proposal 直接实现。单人项目可自审，但必须显式标记 APPROVED。 实现无效，需重新审阅
RED-4 需求变更不更新 spec。Type-A 变更未同步更新 spec.md。 真相源失效，依赖 plan 需重新评估
RED-5 直接修改已锁定的 plan 或 spec。未经 proposal 流程直接修改真相源。 修改无效，必须回退并通过 proposal 重做
RED-6 先实现后补测试。进入编码阶段的第一笔代码不是测试。 视为偏离 TDD，需回退

红
写失败测试
→
绿

→
重构
优化结构
↺

TDD-1 测试先于实现

新增公共接口的测试代码必须在实现代码之前提交。

TDD-2 一个失败测试只写一个

不允许一次性写多个 failing test 再批量实现。

TDD-3 测试必须可独立运行

不依赖其他测试的执行顺序或副作用。

TDD-4 重构必须有测试保护

重构提交时相关测试必须全部通过。

TDD-5 Plan 测试用例全覆盖

plan 中定义的每个测试用例都必须在代码中有对应测试。

🪶 轻量模式（一人团队裁剪版）

当团队规模为 1 人时，以下裁剪是允许的。但某些环节对一人团队反而更重要。

✅ 可裁剪（降低形式成本）

完整流程 轻量裁剪 理由
六阶段（P0-P4） 三阶段（spec+plan → propose → implement+archive） 自评审可省略形式化门槛
tasks 单独文件 plan 内嵌任务清单 一个人不需要任务转手
ADR 单独文件 仅重大决策时写 ADR 常规决策用 plan 内 DC 编号
交叉评审 自审 + checklist 一人团队无交叉评审对象

🚫 不可裁剪（一人团队反而更重要）

constitution.md

给未来自己的约束。3 个月后你会忘记「为什么这样设计」。

spec.md + MoSCoW

范围控制，防止「这个 cool 功能顺手做一下」导致蔓延。

plan + DC 编号

当你回来重构时，DC-0048 告诉你当初为什么这样设计。

proposal 流程

防止「顺手改一下」导致连锁 bug。强制停下来评估。

TDD 红-绿-重构

测试是唯一的代码正确性保障。没有同事帮你 Review。

/sdd-verify

唯一的质量门禁。没有 CI 团队帮你把关。

Greenfield：从零开始

# Step 1: 初始化项目骨架
/sdd-init
  → 选择「轻量版」spec
  → 创建 Document/、SourceCode/ 目录
  → 生成 constitution.md + spec.md 骨架

# Step 2: 填充 spec（对话式）
用户: 核心功能：可视化配置数据流、定时调度、失败告警
      技术栈：Python + FastAPI + React
系统: [生成 spec.md]
      Must: F1 可视化配置, F2 调度执行, F3 失败告警
      关键原则：P1 配置即代码, P2 执行隔离

# Step 3: 模块设计
/sdd-propose
  → 创建 changes/proposal-001.md（Type-B：设计实现）
  → [ADDED] PipelineExecutor 类
  → [ADDED] 状态机定义（IDLE/RUNNING/FAILED/SUCCESS）

# Step 4: TDD 实现
/sdd-implement
  → [RED] 编写 PipelineExecutor 失败测试
  → [GREEN] 实现最小代码
  → [REFACTOR] 优化结构

# Step 5: 归档合并
/sdd-archive
  → 合并到 plan-core.md（新增 DC-0001~0003）
  → 归档 proposal-001
  → 触发 /sdd-verify ✅
